# Aiwa Widget

Widget-first Android interface for Claude Code.

The home-screen widget is the primary product. The full app is a secondary surface for configuration and fallback UI.

Target UX:
- select a Claude Code session
- type or dictate a message
- keep real Claude Code session continuity
- display streaming Claude output
- answer Claude when it asks a question
- send a separate background instruction while work is running
- show working / waiting / finished / error states

Architecture:
Aiwa widget/app -> ClaudeBridge -> local backend (`backend/aiwa_server.py`, in Termux) -> `claude --cloud` -> a Claude Code **cloud session**, visible in the Claude app's Code tab. No API key: the claude.ai login (Pro or above) is used. Aiwa used to run its own `claude` process on the phone; that was removed on request ("je ne veux plus de session tel ou CLI").

The APK does not download or execute Kotlin/DEX from GitHub. Remote configuration is limited to declarative data.

The current Claude Code CLI remains the execution backend because it is not an Android SDK. The backend is hidden from the normal user workflow.

## Status against the target UX

Real and working (as of the polling fix in `LocalClaudeBridge.kt` — see `docs/claude-code.md`):
- type a message and send it, with real Claude output actually reaching the app (the client now polls `/api/events` until a real `done`/`error`, instead of firing one GET that raced the backend and produced nothing) — **but only once a real backend is actually running and reachable; see "Running this for real" below.**
- working / finished / error states (`AiwaState.Status`), now actually wired through `AiwaRepository` and read by both `MainActivity` and the home-screen widget, instead of sitting unused.
- the home-screen widget itself now shows this real, live state instead of static placeholder text — it can't host a real text-input field directly (a hard Android/RemoteViews platform limit, not specific to this app or to Glance), so typing still needs the app, but everything else (see below) works straight from the widget.

Now also real:
- **voice dictation.** `MainActivity`'s 🎙️ button requests `RECORD_AUDIO` at runtime, then launches Android's own `RecognizerIntent.ACTION_RECOGNIZE_SPEECH` and fills the message field with what it heard. Needs a real speech-recognition service on the device (present on virtually all real phones with Google's app installed; may not exist on a bare emulator image).
- **starting the backend automatically.** The app fires Termux's real [`RUN_COMMAND`](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent) automation intent as soon as it opens, running `backend/start.sh` inside the already-installed proot-distro Ubuntu in the background — no manually opening Termux or typing anything, once the one-time setup below has been done at least once. **Honest limits**: this only reports whether Android/Termux *accepted* the request to run the script, not whether the backend actually came up (there's no feedback channel for that yet — the real signal is still whether the next message succeeds); it needs the user to grant the `RUN_COMMAND` permission once (a normal Android permission prompt) **and** to separately turn on `allow-external-apps=true` in Termux's own `~/.termux/termux.properties` — a real security gate of Termux's that this app cannot set on the user's behalf.
- **the widget**: one row of buttons — an "A" button that opens the Aiwa app, a session button (the current cloud session's name, or "Envoi…" while a message is on its way), a grey mic button with a red recording dot (not an emoji), a model button that opens a picker with the models Claude Code documents (exact versions and ids: Fable 5.1 / 5, Opus 5.5 / 5 / 4.8 / 4.7 / 4.6, Sonnet 5.5 / 5 / 4.6, Haiku 4.5, three 1M-context variants, Opus plan) and an **effort** section (Faible / Moyen / Élevé / Très élevé / Max / Auto, like the Claude app's own chip). Each choice is passed as `claude --model` / `--effort` when a NEW cloud session is created **and sent to the open session as `/model <id>` / `/effort <level>` — confirmed on a device for `/model`** (the session answers "Set model to Sonnet 5.5 for this session only"). Known mismatch: the Claude app's own model chip does not follow `/model`, and Aiwa cannot drive it, and, only once a session exists, a "Claude ↗" button that opens that session in the Claude app (the last session in use when the next message will start a new one, e.g. right after choosing a repository). **No conversation text** in the widget or the app: a cloud reply can't be read back by a program, so the conversation lives in the Claude app and is one tap away. One cell high (default 6×2, resizes both ways down to a single row; the second row (see the GitHub bullet) only shows when the widget is at least two cells high). Each list button opens a small floating picker window (`Pickers.kt`): a widget cannot draw an overlay dropdown. No informational messages; real errors of widget actions are toasts (the app shows them in red under its status line). Unverified on a device: that the Claude app opens `https://claude.ai/code/<id>` directly (otherwise the browser does).
- **Instructions integrated into the conversation (GitHub, deployment, alerts).** Claude Code does all of it itself — clone, edit, commit, push, deploy — with its OWN GitHub access, which you grant once at claude.ai/connect-github (a button opens it). Aiwa never logs in to GitHub, never calls its API and never asks for a token: it remembers what you want and adds it, in words, to what is sent (`_compose` in `backend/aiwa_server.py`). The switches: **repository** (the widget picker lists them on its own: the *public* repositories of the owner of the checkout Aiwa was installed from and of the owners of repositories already used — a plain unauthenticated web request, no token — plus the private ones of an already-logged-in `gh` in Termux if there is one; a repository missing from the list can be typed in the app, folded away; choosing one means the next message starts a NEW session there, since a session's repository is fixed when it starts; Aiwa clones it to `~/repos/`, or makes an empty stub whose `origin` is the repository when it is private, and runs `claude --cloud` from there so the cloud session clones the GitHub remote itself); **Push** — in both modes Claude pushes; the switch chooses *where* ("Push: main" = straight to the main branch, no pull request; "Push: branche" = the session's ONE work branch `aiwa/<date>`, main untouched). It applies from the next message, even in the session in progress, and switching back to "main" tells Claude to bring everything done on the work branch back onto main first (merge or fast-forward, no commit lost) — so alternating never leaves work behind, it only decides where it sits meanwhile; the work branch is reused, not recreated, at each switch; **Deploy** (Claude is asked to publish through GitHub Pages with a GitHub Actions workflow, no `gh-pages` branch); **Alerte**, which is mandatory and has no switch (see below); and a **free-text instruction** of your own. The instructions are sent **once**: everything goes with a session's first message; after that only what you changed (a new or altered instruction, or a note that one was withdrawn) — nothing at all when nothing changed. Each session remembers what it was told, and the app shows the exact text of the first message. The buttons appear as you go: repository picker first, then Push and Deploy once a repository is chosen, then `Site ↗`. **The Pages address is known in advance** — `https://<owner>.github.io/<repo>/`, no custom domain — so it is shown as soon as a repository is chosen: in the app (with Open and Copy, and whether it answers), and in the widget once Deploy is on or the address answers (orange = it answers to a plain web request, grey = not yet, it still opens). Documented push protection: in an Anthropic-hosted session `git push` only works on the session's current branch, and GitHub branch protection still applies. **Unverified on a device:** all of it, in particular that `claude --cloud` started from that directory uses the GitHub remote (Anthropic documents it; without Claude's GitHub access it would upload the stub instead — the instructions ask Claude to check `git remote -v` and say so), and that Claude Code actually creates the Pages workflow and, when it has a notification tool, alerts.
- **not built, on purpose** (an automatic safety review of my own work refused them; they need your explicit go-ahead, not a general "do everything"): a button in Aiwa that starts a GitHub authorization or confirms `/web-setup` (the token hand-over to Anthropic) for you; Aiwa calling the GitHub API to enable Pages or commit a workflow itself; and notification *hooks* committed into `.claude/settings.json`. The alert above is the prompt-only substitute.
- **Importing an existing session by the name of its branch.** Copy the session's link (`claude.ai/code/session_…`) *or* the name of its branch (`claude/…`) in Claude Code and tap "Ajouter une session existante": for a branch, the backend looks it up in the repositories it knows (the chosen one, the ones of remembered sessions, the discovered list; a plain `git ls-remote`/`fetch`, no token for public repositories) and reads the `Claude-Session: https://claude.ai/code/session_…` line that a cloud session's commits carry — only commits that are on the branch and not on the default branch count, so a brand-new branch is never mistaken for an older session. It imports the session on its own branch (the only one Claude can push to). Fails with a plain reason that lists every repository it tried and what it found there ("branche absente" / "privé ou inaccessible"): **a private repository cannot be read by Aiwa** (no token), so for those copy the session's link (`claude.ai/code/session_…`) instead, or the `claude --teleport session_…` command if the session menu offers it (the id inside is enough). Also fails when none of the branch's commits carries the link yet (the session has to have committed once). At most ~35 s. Unverified on a device.
- **Model and effort are remembered per session** (each session keeps what was last asked for it; picking a session brings its own back into the widget), because the Claude app's own model chip does not follow `/model` and a single global value made the two drift apart.
- **"Claude attend" in the widget (mandatory).** The CLI can't read a cloud reply back, so Claude is told, in the first message of a session, to run `curl -s -m 5 -d attend https://ntfy.sh/<random topic>` at the end of every answer (when it is done or waits for an answer, a decision, a validation). The backend listens to that topic on a public relay (`ntfy.sh`; the topic is a random secret kept in `~/.aiwa_state.json`) and `KeepAliveService` polls the backend every 10 s, so the widget's `Claude ↗` button turns red with a dot ("● Claude attend ↗") until you answer or open the session. No push notification, no hook, nothing written into a repository. **Two things must be true, both unverified**: Claude keeps following the instruction on every turn, and the cloud environment lets `curl` reach `ntfy.sh` (the default *Trusted* network access does not: environment menu → Edit → Network access → Custom → add `ntfy.sh`; a blocked ping is harmless). The app has a test button (phone side only: it pings the relay itself) and shows when the last ping arrived.
- **the widget follows the backend, not a local guess.** The widget observes `AiwaRepository` reactively instead of capturing a snapshot in `provideGlance` — Glance keeps a composition alive for a while and answers `updateAll()` by recomposing that same composition, so a captured snapshot stayed stale (the header lagged behind the app). `BackendSync` is the one place that copies the backend's real session/model/session list into `AiwaRepository`; the refresh that started last always wins.
- **the backend keeps itself up to date.** Every time the app launches the backend it runs an inline `bash -c` in Termux that fast-forwards the `~/aiwa_widget` checkout (`git pull --ff-only`), restarts the server only if the code changed, and doesn't start a second server if one already answers. `/api/status` reports a `version`; the app compares it with `EXPECTED_BACKEND_VERSION` (bump both together) and forces one restart if the running server is older. Nothing depends on a script file existing in the checkout any more — the earlier `backend/open-session.sh` (and the widget's "open in Claude Code" entry that used it) was removed: on a stale checkout it didn't exist and Termux answered "executable regular file not found" (its error 150).
- **the widget's mic** opens `DictateActivity`, a small translucent activity (own task via `taskAffinity=""`, so it doesn't drag `MainActivity` to the front). It is kept warm by `KeepAliveService` (a foreground service with a permanent low-priority notification), started on app open, on boot and after an app update (`BootReceiver`), and whenever the mic is used. **Honest limit**: unverified on a real device whether the first-tap flash is fully gone.
- **cloud sessions are the only mode.** New session: `claude --cloud "<message>"` run (through `script`, so the CLI gets a real terminal, as in the manual test that worked) from a tiny local git repo `~/chat-cloud` inside the proot Ubuntu, created on first use — Anthropic documents that a local repo with at least one commit is uploaded as a bundle, no GitHub needed. Follow-up: `claude -p --cloud <session-id> --output-format json` with the message on stdin. The session id is read from the CLI's output (`session_…`/`cse_…` or the `claude.ai/code/…` link). **Existing cloud sessions can't be listed** (no non-interactive CLI command for it), so the picker lists the ones Aiwa created plus any added with "Ajouter une session (lien copié)" — copy the session's address (`claude.ai/code/session_…`) first. **Session names**: Claude names a cloud session itself and the CLI can't read that name back, so the two names used to differ. Aiwa now imposes its own: right after creating a session the backend queues `/rename <first words of the message>` (documented for cloud sessions, same argument form as `/model`), so Aiwa and the Claude app show the same name. Unverified on a device: that the queued `/rename` runs as a command, and that it wins over Claude's own automatic title. The current session and model survive a backend restart (`~/.aiwa_state.json`). **Honest limits**: the CLI only queues a message and returns — there is no documented way to read a cloud reply back, so Aiwa shows no conversation and the answer is read in the Claude app ("Claude ↗" in the widget, "Ouvrir Claude" in the app opens it). Creating a session stops the `claude --cloud` process a few seconds after the session id appears (it may otherwise stay open waiting on the terminal; without this a send waited up to 3 minutes), and `~/aiwa_cloud_last.log` records a timeline of the run. If creating a session fails, the whole output of the CLI is in `~/aiwa_cloud_last.log` inside the Ubuntu (`proot-distro login ubuntu -- cat /root/aiwa_cloud_last.log`).

Still not real — never built, not by this session and not before it, whatever the "Fond" wording might suggest:
- **background instruction while work is running.** `/api/background` deliberately returns `not wired yet`; the "Fond" button that called it was removed from `MainActivity` rather than leave a control that always silently fails. The persistent-process change above is a prerequisite for this (now in place) but doesn't by itself implement sending a second instruction while the first is still being answered — that's a distinct, still-unbuilt feature.
- **answering a mid-conversation question from Claude.** `AiwaState.WAITING`/`question` exist in the model, but a cloud session's questions are answered in the Claude app; nothing in Aiwa detects them.
- no automated tests, on either the Kotlin or the Python side.

## Running this for real

Installing the APK is not enough on its own — the app only ever talks to `127.0.0.1:8787` (see `docs/claude-code.md`), and nothing in this repo starts that server for you. **`backend/aiwa_server.py` (and the `claude` CLI itself) has to actually be running on the SAME device the app is installed on** — `127.0.0.1` is per-device loopback, so a server running on a separate computer is not reachable this way at all, port-forwarding aside. "fail to connect to 127.0.0.1:8787" means exactly this: nothing is listening there yet, not a bug in the app.

**Honest tradeoff, worth knowing before setting this up**: `claude` is a real dev-tool CLI, built to operate on a real project's files on a real computer — running it via Termux puts it on your *phone's* filesystem, disconnected from whatever project you actually work on at your computer. That's a real architectural limitation of this design, not just a rough edge — a backend running on your own computer instead, with the app connecting to it remotely, would be a better fit for "check on / steer a Claude Code session while away from your desk," but is a bigger change (real auth, a configurable server address instead of a hard-coded `127.0.0.1`) that hasn't been built here. This was raised explicitly and the on-phone-via-Termux design was kept on purpose.

**Bigger honest limit, confirmed live and not fixable from this repo alone**: Anthropic does not publish a `claude-code` native binary for `linux-arm64-android` at all (Termux's own platform) — only for `linux-arm64`/`linux-x64`/their musl variants, macOS and Windows. The workaround below runs a real Ubuntu userland inside Termux (via `proot-distro`, no real virtualization, no network namespace — `127.0.0.1` inside it is genuinely the same loopback the app itself uses) so `claude` installs as plain `linux-arm64` instead. **This has not been verified end-to-end against a real device by this project** — it is the most plausible known fix for this class of problem on Termux, not a guarantee.

On a real phone, install [Termux](https://termux.dev/) (a real terminal app, not this project's own code — get it from F-Droid; the Play Store build is outdated and often broken) and [Termux:API](https://wiki.termux.com/wiki/Termux:API) (needed for the wake-lock), then run this ONE command, from anywhere — it always installs/updates a fixed `$HOME/aiwa_widget` regardless of whatever directory Termux happens to resume you in, so there's no "which folder am I in" step and the exact same command is also how you update later:
```
curl -fsSL https://raw.githubusercontent.com/theodoreyong9/aiwa_widget/main/backend/bootstrap.sh | bash
```
This installs `proot-distro` and a real Ubuntu image the first time (a real, sizeable download), installs Node.js/Python/the Claude Code CLI inside it, takes a wake-lock so Android doesn't kill Termux the moment you switch to the Aiwa app, and starts the server — all inside that Ubuntu environment. Leave that Termux session running for as long as you want the app to work; closing Termux or letting Android kill it stops the backend, and re-running the same command above restarts it. Nothing here survives a reboot on its own. (`backend/setup-termux.sh`, the plain-Termux-no-Ubuntu version, is kept in the repo for reference but does not work as-is given the missing native binary above.)

**After that one-time setup**, you don't need to open Termux by hand again for daily use: add `allow-external-apps=true` to `~/.termux/termux.properties` inside Termux once (`echo "allow-external-apps=true" >> ~/.termux/termux.properties && termux-reload-settings`), grant Aiwa the "run commands" permission when Android asks, and opening the app will start the backend for you via Termux's own `RUN_COMMAND` API. If it never seems to actually come up, fall back to running the `curl | bash` command above by hand to see the real output/errors.

## Reinstalling without uninstalling first

CI now signs every debug build with a fixed, committed `debug.keystore` at the repo root (the well-known public Android debug convention — alias/password `android`, never a real secret) instead of AGP's own default of auto-generating a different one per machine. Every GitHub Actions run is a fresh machine, so before this fix each build's APK had a genuinely different signing key, and Android refuses to install an APK over an existing one when the signatures don't match — hence needing to uninstall every time. Installing a new `aiwa-debug.apk` over the old one should now work as a normal update (keeping app data) as long as both were built after this fix.
