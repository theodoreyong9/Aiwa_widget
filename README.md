# Aiwa Widget

Widget-first Android interface for Claude Code.

The home-screen widget is the primary product. The full app is a secondary surface for configuration and fallback UI.

Target UX:
- select a Claude Code session
- type or dictate a message
- keep real Claude Code session continuity
- display streaming Claude output
- answer Claude when it asks a question
- send a separate background instruction while work is running
- show working / waiting / finished / error states

Architecture:
Aiwa widget/app -> ClaudeBridge -> local backend (`backend/aiwa_server.py`, in Termux) -> `claude --cloud` -> a Claude Code **cloud session**, visible in the Claude app's Code tab. No API key: the claude.ai login (Pro or above) is used. Aiwa used to run its own `claude` process on the phone; that was removed on request ("je ne veux plus de session tel ou CLI").

The APK does not download or execute Kotlin/DEX from GitHub. Remote configuration is limited to declarative data.

The current Claude Code CLI remains the execution backend because it is not an Android SDK. The backend is hidden from the normal user workflow.

## Status against the target UX

Real and working (as of the polling fix in `LocalClaudeBridge.kt` — see `docs/claude-code.md`):
- type a message and send it, with real Claude output actually reaching the app (the client now polls `/api/events` until a real `done`/`error`, instead of firing one GET that raced the backend and produced nothing) — **but only once a real backend is actually running and reachable; see "Running this for real" below.**
- working / finished / error states (`AiwaState.Status`), now actually wired through `AiwaRepository` and read by both `MainActivity` and the home-screen widget, instead of sitting unused.
- the home-screen widget itself now shows this real, live state instead of static placeholder text — it can't host a real text-input field directly (a hard Android/RemoteViews platform limit, not specific to this app or to Glance), so typing needs the app — a bare full-page text field and a send button (see "The app" below) — but everything else works straight from the widget.

Now also real:
- **voice dictation.** The widget's mic (`DictateActivity`) requests `RECORD_AUDIO` at runtime, then listens (Android's own speech recognizer) until you say the stop phrase and sends what it heard; the app itself has no mic button any more (asked for: only the text field and send). Needs a real speech-recognition service on the device (present on virtually all real phones with Google's app installed; may not exist on a bare emulator image).
- **starting the backend automatically.** The app fires Termux's real [`RUN_COMMAND`](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent) automation intent as soon as it opens, running `backend/start.sh` inside the already-installed proot-distro Ubuntu in the background — no manually opening Termux or typing anything, once the one-time setup below has been done at least once. **Honest limits**: this only reports whether Android/Termux *accepted* the request to run the script, not whether the backend actually came up (there's no feedback channel for that yet — the real signal is still whether the next message succeeds); it needs the user to grant the `RUN_COMMAND` permission once (a normal Android permission prompt) **and** to separately turn on `allow-external-apps=true` in Termux's own `~/.termux/termux.properties` — a real security gate of Termux's that this app cannot set on the user's behalf.
- **the widget**: one row of buttons — an "A" button that opens the Aiwa app, a session button (the current cloud session's name, or "Envoi…" while a message is on its way), a grey mic button with a red recording dot (not an emoji), a model button that opens a picker with the models Claude Code documents (exact versions and ids: Fable 5.1 / 5, Opus 5.5 / 5 / 4.8 / 4.7 / 4.6, Sonnet 5.5 / 5 / 4.6, Haiku 4.5, three 1M-context variants, Opus plan) and an **effort** section (Faible / Moyen / Élevé / Très élevé / Max / Auto, like the Claude app's own chip). Each choice is passed as `claude --model` / `--effort` when a NEW cloud session is created **and sent to the open session as `/model <id>` / `/effort <level>` — confirmed on a device for `/model`** (the session answers "Set model to Sonnet 5.5 for this session only"). The Claude app's own model chip lagged one step behind `/model` at first; the user reports that it follows now (not verified here). Only once a session exists, there is also a "Claude ↗" button that opens that session in the Claude app (the last session in use when the next message will start a new one, e.g. right after choosing a repository). **No conversation text** in the widget or the app: a cloud reply can't be read back by a program, so the conversation lives in the Claude app and is one tap away. One cell high (default 6×2, resizes both ways down to a single row; the second row (see the GitHub bullet) only shows when the widget is at least two cells high). Each list button opens a small floating picker window (`Pickers.kt`): a widget cannot draw an overlay dropdown. No informational messages; real errors of widget actions are toasts (the app shows them in red under its status line). Unverified on a device: that the Claude app opens `https://claude.ai/code/<id>` directly (otherwise the browser does).
- **Instructions integrated into the conversation (GitHub, deployment, alerts).** Claude Code does all of it itself — clone, edit, commit, push, deploy — with its OWN GitHub access, which you grant once at claude.ai/connect-github (a button opens it). Aiwa never logs in to GitHub, never calls its API and never asks for a token: it remembers what you want and adds it, in words, to what is sent (`_compose` in `backend/aiwa_server.py`). The switches: **repository** (the widget picker lists them on its own: the *public* repositories of the owner of the checkout Aiwa was installed from and of the owners of repositories already used — a plain unauthenticated web request, no token — plus the private ones of an already-logged-in `gh` in Termux if there is one; a repository that is not in the list (a private one Aiwa cannot read) can no longer be added by hand — the field for it was in the app's settings card, removed with it (`git log -- app/src/main/java/com/aiwa/widget/GithubCard.kt` has it); choosing one means the next message starts a NEW session there, since a session's repository is fixed when it starts; Aiwa clones it to `~/repos/`, or makes an empty stub whose `origin` is the repository when it is private, and runs `claude --cloud` from there so the cloud session clones the GitHub remote itself); **Push** — Claude always works on its own branch (`aiwa/<date>`, or the branch of an imported session). "Push: main": after every finished change it integrates its WHOLE branch into the main branch (commits made while integration was off included) and pushes it — a direct push if the session allows it, otherwise a pull request merged at once — after checking that main received no parallel change that conflicts (the push lands on main — the branch GitHub Pages deploys — unless Pages is set up on the session's own branch); on a conflict, or any doubt, it integrates nothing and asks you; never a force-push. "Push: branche": it pushes only its branch, main is untouched, everything is integrated at the next switch to "main". Applies from the next message, even in the session in progress; **Verification** (whenever a repository is chosen): before saying it is done Claude reads ALL the logs it can reach — test/lint/build output, the logs of whatever server or script it runs, the GitHub Actions and deployment logs after a push (failed jobs included), the browser console (errors, warnings, unhandled exceptions), failed network requests and page errors gathered with Playwright (`page.on('console')`, `'pageerror'`, `'requestfailed'`, responses with status >= 400; Chromium is already installed in cloud sessions) and any other journal in its environment — fixes what it finds, checks the UX of a web interface (local, then the published address; mobile and desktop widths, screenshots, overflow, main paths) and reports what it read, what it could NOT reach and what stays doubtful; **Deploy** (Claude is asked to publish through GitHub Pages with a GitHub Actions workflow, no `gh-pages` branch); **Alerte**, which is mandatory and has no switch (see below). (A free-text instruction used to be a seventh one; its only editor was the app's settings card, so it is no longer sent — write such a note as a message.) The instructions are sent **once**: everything goes with a session's first message; after that only what you changed (a new or altered instruction, or a note that one was withdrawn) — nothing at all when nothing changed. Each session remembers what it was told; the exact text is the first message of the conversation in the Claude app. **With no repository chosen (free chat) only the alert line is sent**: Push, Deploy and Verification (logs, Playwright…) are added only once a repository is chosen. The buttons appear as you go: repository picker first, then Push and Deploy once a repository is chosen, then `Site ↗`. **The Pages address is known in advance** — `https://<owner>.github.io/<repo>/`, no custom domain — so it is known as soon as a repository is chosen: the widget shows it once Deploy is on or the address answers (orange = it answers to a plain web request, grey = not yet, it still opens). The state of the **GitHub Actions** (latest run: success / failure / running, from the public API, at most every 150 s) is an `Actions ✓ ↗` pill in the widget, one tap from the run. The two round buttons after Deploy are the site (globe: orange when its address answers, grey otherwise) and the Actions (play button: green / red / grey for success / failure / running or unknown). **"Ready to see"**: when a NEW green run appears (a push landed and the Actions passed; the first run ever seen is only a baseline), the widget shows a mint `● Prêt ↗` pill in place of the two round buttons until you tap it; it opens the site if its address answers, else the run. Documented push protection: in an Anthropic-hosted session `git push` only works on the session's current branch, and GitHub branch protection still applies. **Unverified on a device:** all of it, in particular that `claude --cloud` started from that directory uses the GitHub remote (Anthropic documents it; without Claude's GitHub access it would upload the stub instead — the instructions ask Claude to check `git remote -v` and say so), and that Claude Code actually creates the Pages workflow and, when it has a notification tool, alerts.
- **not built, on purpose** (an automatic safety review of my own work refused them; they need your explicit go-ahead, not a general "do everything"): a button in Aiwa that starts a GitHub authorization or confirms `/web-setup` (the token hand-over to Anthropic) for you; a **token / plan-usage bar**: no documented way exists for a program to read the usage of a cloud session (see the reply of that day: the 5-hour and weekly percentages are only given to the status line of a local interactive Claude Code, and the community routes go through the account's login token, which Aiwa does not touch without an explicit go-ahead); Aiwa calling the GitHub API to enable Pages or commit a workflow itself; and notification *hooks* committed into `.claude/settings.json`. The alert above is the prompt-only substitute.
- **Importing an existing session by the name of its branch.** Copy the session's link (`claude.ai/code/session_…`) *or* the name of its branch (`claude/…`) in Claude Code and tap "Ajouter une session existante": for a branch, the backend looks it up in the repositories it knows (the chosen one, the ones of remembered sessions, the discovered list; a plain `git ls-remote`/`fetch`, no token for public repositories) and reads the `Claude-Session: https://claude.ai/code/session_…` line that a cloud session's commits carry — only commits that are on the branch and not on the default branch count, so a brand-new branch is never mistaken for an older session. It imports the session on its own branch (the only one Claude can push to). Fails with a plain reason that lists every repository it tried and what it found there ("branche absente" / "privé ou inaccessible"): **a private repository cannot be read by Aiwa** (no token), so for those copy the session's link (`claude.ai/code/session_…`) instead, or the `claude --teleport session_…` command if the session menu offers it (the id inside is enough). Also fails when none of the branch's commits carries the link yet (the session has to have committed once). At most ~35 s. Unverified on a device.
- **Model and effort are remembered per session** (each session keeps what was last asked for it; picking a session brings its own back into the widget), because the Claude app's own model chip lagged behind `/model` at first and a single global value made the two drift apart.
- **"Claude attend" in the widget (mandatory).** The CLI can't read a cloud reply back, so Claude is told, in the first message of a session, to run `curl -s -m 5 -d attend https://ntfy.sh/<random topic>` at the end of every answer (when it is done or waits for an answer, a decision, a validation). The backend listens to that topic on a public relay (`ntfy.sh`; the topic is a random secret kept in `~/.aiwa_state.json`) and `KeepAliveService` polls the backend every 10 s, so the widget's `Claude ↗` button turns red with a dot ("● Claude attend ↗") until you answer or open the session. No push notification, no hook, nothing written into a repository. **Two things must be true, both unverified**: Claude keeps following the instruction on every turn, and the cloud environment lets `curl` reach `ntfy.sh` (the default *Trusted* network access does not: environment menu → Edit → Network access → Custom → add `ntfy.sh`; a blocked ping is harmless).
- **the widget follows the backend, not a local guess.** The widget observes `AiwaRepository` reactively instead of capturing a snapshot in `provideGlance` — Glance keeps a composition alive for a while and answers `updateAll()` by recomposing that same composition, so a captured snapshot stayed stale (the header lagged behind the app). `BackendSync` is the one place that copies the backend's real session/model/session list into `AiwaRepository`; the refresh that started last always wins.
- **the backend keeps itself up to date.** Every time the app launches the backend it runs an inline `bash -c` in Termux that fast-forwards the `~/aiwa_widget` checkout (`git pull --ff-only`), restarts the server only if the code changed, and doesn't start a second server if one already answers. `/api/status` reports a `version`; the app compares it with `EXPECTED_BACKEND_VERSION` (bump both together) and forces one restart if the running server is older. Nothing depends on a script file existing in the checkout any more — the earlier `backend/open-session.sh` (and the widget's "open in Claude Code" entry that used it) was removed: on a stale checkout it didn't exist and Termux answered "executable regular file not found" (its error 150).
- **Backend start, loading indicator, self-restart.** Reported live: the Termux backend took ages to come up and the widget gave no sign of it. What was cut: `start.sh` no longer enters proot twice (it has no "is Ubuntu installed?" pre-check at all any more — a first version tested the proot-distro directory, guessed its location wrong on a real phone and made every start exit silently; if Ubuntu is missing, proot-distro says so in the log), the inline Termux script bounds `git pull` to 15 s and waits for the port to answer (checks every 0.5 s, at most 4 s) instead of a fixed `sleep 2`, and after an update the app waits up to 45 s for the new version before forcing at most ONE restart (it used to restart a backend that was merely still starting). The cold start of proot itself and of Python is not something Aiwa can shorten; expect several seconds. While it runs the session pill of the widget reads "⏳ Démarrage…", and "⚠ Backend arrêté" when it does not answer; `KeepAliveService` (polls every 10 s) asks Termux to start it again by itself, at most once every 90 s. **One start at a time.** The app, the keep-alive service and the pickers can each ask Termux for a start; while the port is not open yet each ask used to launch its own proot Ubuntu, and several at once made the phone crawl (reported: "une méga plombe"). `start.sh` now keeps its pid in `~/.aiwa_start.pid` while it runs and the launcher script exits at once when a start is already in progress (`already in progress` in `~/aiwa_start.log`); a forced restart still works (kills the old server, waits for it, starts the new one). The `git pull` is bounded to 8 s, and every step is timed in the logs. Two logs in Termux's home tell what happened: `~/aiwa_start.log` (what the launcher script Aiwa sends to Termux did: git pull, restart, start — if it is missing or old, Termux never ran the script: RUN_COMMAND permission / `allow-external-apps`) and `~/aiwa_backend.log` (written first by `start.sh`, then the server's own output and exit code): `cat ~/aiwa_start.log ~/aiwa_backend.log`. Unverified on a device: how much faster it really is.
  **What starts the backend without opening the app.** It used to be only the app itself (and a picker, or the mic): the widget on its own started nothing, so after a reboot or a killed Termux you had to open Aiwa first. The keep-alive service is what restarts it, so now every way Aiwa's process comes to life starts that service (`wakeAiwa`: process start, widget redraw/placement, each widget tap that opens a window, boot, app update), and the service also updates and restarts once an older server that still answers after an app update. Android may refuse a service start from the background with no user action (a launcher redraw); the next tap then does it. Termux itself must still allow it (`allow-external-apps=true`, the RUN_COMMAND permission granted once).
- **The last known state survives** (`AiwaApp` restores a snapshot from SharedPreferences when the process starts; every successful refresh writes it). Reported live: "Claude ↗" vanished — the widget only knew the session from the backend's answer, so a freshly started process with the backend still down/starting had no session and drew no button. It now shows the last session/repository until the backend answers (the backend stays the truth and overwrites it); `/api/status` also reports `last_session` (falls back to the most recent stored session) so the button exists after a repository was chosen, too.
- **Widget picker preview.** `aiwa_widget_info.xml` gives Android 12+ launchers a real preview layout (`previewLayout`: the two rows of the widget drawn with plain views) and older ones a vector drawing (`previewImage`, shapes only, no text), plus a description; `initialLayout` is a small "Aiwa · chargement…" pill instead of a blank one. The widget is now **not resizable** (`resizeMode="none"`, 4 cells wide × 2 high; remove and re-add it to see the change) and draws four bands that share the whole height, on a dark gradient card: (1) the neutral `A` (opens the app), the session name (tap = session picker) with a status line under it — "Prêt", "Envoi en cours…", "⏳ Démarrage du backend…", "⚠ Backend arrêté — relance en cours", or, in red, "● Claude attend ta réponse" — and the round orange Claude spark (red while Claude waits, and the card gets a red edge and warm tint); (2) repository chip and model chip, half the width each; (3) once a repository is chosen: `Push main`/`Push branche`, `Deploy ○/●` / `Android ●` (tap to cycle), and the round globe or download (orange = the address answers) and Actions (green / red / grey = success / failure / running or unknown) buttons, or the mint `● Prêt ↗` in their place after a new green run; (4) the big grey dictation button with its red recording dot. Without a repository band 3 is absent and the others share its height. Buttons grow with their band up to a comfortable size (44 dp; the dictation button 48 dp), so a taller cell gets roomier, not emptier. Nothing is ever hidden: chips share the width, and the text of the session and the repository is cut with `…` to an estimate of what fits (`AiwaWidget.kt`, from the characters and the font scale); Push's label shortens to `main`/`branche` when narrow. The old two-row layout is kept as `CompactContent`, only for a launcher whose cells make the widget under 150 dp high. Icons are vector drawables (`ic_claude`, `ic_globe`, `ic_actions`), the card `widget_bg` / `widget_bg_alert`; the picker preview (`aiwa_widget_preview.xml`, and the vector fallback) draws the same four bands. Text widths are estimates and the layout was checked in an HTML mock, not on a device.
- **Deploy is a list, not a cycle** (`DeployPickerActivity`, opened by the chip; it cycled through the states at each tap before, which was too many to walk through): Aucun déploiement / Site web (GitHub Pages) / Application Android (an APK) / Sphère YourMine / Aiwa; exclusive. *Android* adds an instruction asking Claude to keep a GitHub Actions workflow that builds the debug APK on every push to the main branch, signs it with a fixed debug key committed in the repository (so successive APKs install over each other), and publishes it as `<repo>.apk` in ONE rolling GitHub release tagged `android-latest` (file replaced at each build, tag moved), never committed to the repository. Aiwa's own workflow used to commit its APK (47 commits of 11 MB, about 490 MB of history); it now does the same as the Android mode: `Aiwa_widget.apk` in the rolling release `android-latest`, recreated at each build (`gh release delete` + `create`, serialized by a `concurrency` group), address `https://github.com/theodoreyong9/Aiwa_widget/releases/download/android-latest/Aiwa_widget.apk`. The download address is known in advance (`https://github.com/<owner>/<repo>/releases/download/android-latest/<repo>.apk`); in this mode the widget's round site button becomes a download button (orange when the address answers, probed with a one-byte range request) and the mint `Prêt` opens it. Switching modes sends only the changed instruction ("Consigne retirée : déploiement." when going back to nothing). Old state files that only knew yes/no are read as Pages. If the repository is not an Android project Claude is told to say so and do nothing. Unverified on a device, like the Pages workflow: that Claude sets the workflow up correctly.
- **Several repositories in one message.** The repository picker of the widget has a line "＋ Autres dépôts où Claude peut intervenir…" (once a primary repository is chosen): a second window where any number of the listed repositories (8 at most) are checked, the window staying open. The widget's repository chip then reads `⎇ name +2`. Backend 15: `extra_repos` (persisted; `POST /api/github/extra` toggles one, an empty body clears; choosing an extra as the primary removes it from the extras) and the `repo` instruction line names them: Claude "may also work on" A and B, and is asked to attach each itself with the `add_repo` tool when it needs it (`push` access if it must push), to tell the user if the tool is missing or access is refused, to touch no other repository, and to apply the Push and Verification rules to each (its own branch, never a force-push). **This is a text: it grants nothing.** What Claude can reach is decided by the platform — the GitHub connection of the Claude account and the repositories attached to the session; a session's repositories are chosen when it starts and `claude --cloud`, which Aiwa uses, starts one on the current repository only, hence the request to attach the others during the session. Unverified on a device: that `add_repo` exists in a session started by `claude --cloud`, and that Claude uses it as asked. Only one GitHub account can be connected to the Claude account (feature requests for several are open): repositories of other owners are reachable when that account has access to them (collaborator, organisation); public ones can be read anonymously either way.
- **GitHub connection.** The connection Claude Code uses is Claude's own, made in Claude's settings; Aiwa never logs in to GitHub. The repository picker of the widget ends with ONE entry that opens Claude's list of connectors (`claude.ai/customize/connectors`): that page shows the real state and offers Connect or Disconnect accordingly, and switching account is disconnect then connect. Aiwa cannot know whether GitHub is connected, so it cannot show Connect only when disconnected (two entries used to be shown, always both). If the Claude GitHub App also has to be installed on a repository, that step is at `claude.ai/connect-github`. Aiwa starts its sessions with `claude --cloud`, which is documented to create one for the current repository only, so a session started by Aiwa has one; to use several, start the session in the Claude app and add it to Aiwa by its link ("Ajouter une session existante"). ## Running this for real

Installing the APK is not enough on its own — the app only ever talks to `127.0.0.1:8787` (see `docs/claude-code.md`), and nothing in this repo starts that server for you. **`backend/aiwa_server.py` (and the `claude` CLI itself) has to actually be running on the SAME device the app is installed on** — `127.0.0.1` is per-device loopback, so a server running on a separate computer is not reachable this way at all, port-forwarding aside. "fail to connect to 127.0.0.1:8787" means exactly this: nothing is listening there yet, not a bug in the app.

**Honest tradeoff, worth knowing before setting this up**: `claude` is a real dev-tool CLI, built to operate on a real project's files on a real computer — running it via Termux puts it on your *phone's* filesystem, disconnected from whatever project you actually work on at your computer. That's a real architectural limitation of this design, not just a rough edge — a backend running on your own computer instead, with the app connecting to it remotely, would be a better fit for "check on / steer a Claude Code session while away from your desk," but is a bigger change (real auth, a configurable server address instead of a hard-coded `127.0.0.1`) that hasn't been built here. This was raised explicitly and the on-phone-via-Termux design was kept on purpose.

**Bigger honest limit, confirmed live and not fixable from this repo alone**: Anthropic does not publish a `claude-code` native binary for `linux-arm64-android` at all (Termux's own platform) — only for `linux-arm64`/`linux-x64`/their musl variants, macOS and Windows. The workaround below runs a real Ubuntu userland inside Termux (via `proot-distro`, no real virtualization, no network namespace — `127.0.0.1` inside it is genuinely the same loopback the app itself uses) so `claude` installs as plain `linux-arm64` instead. **This has not been verified end-to-end against a real device by this project** — it is the most plausible known fix for this class of problem on Termux, not a guarantee.

On a real phone, install [Termux](https://termux.dev/) (a real terminal app, not this project's own code — get it from F-Droid; the Play Store build is outdated and often broken) and [Termux:API](https://wiki.termux.com/wiki/Termux:API) (needed for the wake-lock), then run this ONE command, from anywhere — it always installs/updates a fixed `$HOME/aiwa_widget` regardless of whatever directory Termux happens to resume you in, so there's no "which folder am I in" step and the exact same command is also how you update later:
```
curl -fsSL https://raw.githubusercontent.com/theodoreyong9/aiwa_widget/main/backend/bootstrap.sh | bash
```
The same command also downloads the latest APK (`backend/install-apk.sh`, which can be run alone: `bash ~/aiwa_widget/backend/install-apk.sh`) and asks Android's installer to open it — you still have to tap Install/Update. It checks what it downloaded (an APK is megabytes; a failed transfer or an error page is not kept and is reported as *NOT downloaded*), keeps the file at `~/aiwa-debug.apk`, and, once `termux-setup-storage` has been run, also as `Aiwa_widget.apk` in the phone's Downloads folder, so the Files app can open it when no installer appears; its last lines are printed again just before the server starts, since the setup in between is long. If a backend is already running (started by the app, or by a previous run), the command now stops it first — it used to die with `Address already in use` and leave the old backend, with the old code, answering. This installs `proot-distro` and a real Ubuntu image the first time (a real, sizeable download), installs Node.js/Python/the Claude Code CLI inside it, takes a wake-lock so Android doesn't kill Termux the moment you switch to the Aiwa app, and starts the server — all inside that Ubuntu environment. Leave that Termux session running for as long as you want the app to work; closing Termux or letting Android kill it stops the backend, and re-running the same command above restarts it. Nothing here survives a reboot on its own. (`backend/setup-termux.sh`, the plain-Termux-no-Ubuntu version, is kept in the repo for reference but does not work as-is given the missing native binary above.)

**After that one-time setup**, you don't need to open Termux by hand again for daily use: add `allow-external-apps=true` to `~/.termux/termux.properties` inside Termux once (`echo "allow-external-apps=true" >> ~/.termux/termux.properties && termux-reload-settings`), grant Aiwa the "run commands" permission when Android asks, and opening the app will start the backend for you via Termux's own `RUN_COMMAND` API. If it never seems to actually come up, fall back to running the `curl | bash` command above by hand to see the real output/errors.

## Reinstalling without uninstalling first

CI now signs every debug build with a fixed, committed `debug.keystore` at the repo root (the well-known public Android debug convention — alias/password `android`, never a real secret) instead of AGP's own default of auto-generating a different one per machine. Every GitHub Actions run is a fresh machine, so before this fix each build's APK had a genuinely different signing key, and Android refuses to install an APK over an existing one when the signatures don't match — hence needing to uninstall every time. Installing a new `aiwa-debug.apk` over the old one should now work as a normal update (keeping app data) as long as both were built after this fix.
